# Release Candidate Policy — forge-doctor-data 1.0

This document is the governing policy for the `1.0.0-rcN` cycle. It
defines what is frozen, what may still change, and the discipline that
applies between `rc1` and `1.0.0`. The baseline reference point is
[`rc-baseline.json`](rc-baseline.json), regenerated by
`tools/rc_baseline.py`; `tools/rc_baseline.py --check` fails when a
frozen measurement moved.

## 1. Architectural freeze

During the RC cycle the following are **frozen**:

- `DataPlatformGraph` core semantics
- `EntityKind`, `RelKind`, `EvidenceKind` vocabularies
- `forge-contracts/1` (the wire contract family)
- Public Python API (`forge_doctor_data.api.__all__`)
- Plugin SDK v2
- MCP stable tools (the 13 tools listed in `rc-baseline.json`)
- CLI stable commands and groups (`docs/api-surface.json`, `cli`)
- JSON/SARIF output schemas (`SCAN_SCHEMA_VERSION`, `JSON_SCHEMA_VERSION`)
- `HandoffBundle` wire shape
- Forger boundary semantics (`x-forge-data` request surface)

A breaking change to any frozen surface requires **all** of:

1. an explicit maintainer decision (recorded in the PR),
2. a migration note in the changelog and in `docs/deprecation.md`,
3. a version-impact analysis (does it restart RC numbering?).

## 2. Stability classes

`docs/api-surface.json` tags every public surface with one of the
adopted stability classes:

| Class | Meaning |
| --- | --- |
| `stable` | semver-bound; removal or rename requires a MAJOR bump |
| `wire` | external contract; follows its own version family |
| `ux` | CLI surface; governed by `docs/deprecation.md` |

`EXPERIMENTAL`/`INTERNAL` surfaces exist but are intentionally absent
from the frozen inventory; `DEPRECATED` is expressed through
`docs/deprecation.md`, not a surface tag. No surface may be promoted to
`stable` without tests, docs, consumer evidence, and a compatibility
story.

## 3. RC no-feature rule

During RC:

- **Allowed:** bug fixes, false-positive fixes, false-negative fixes,
  performance fixes, documentation fixes, compatibility fixes.
- **Forbidden:** new vendors, new major models/ontology families,
  public schema redesign, new top-level platform features.

## 4. Post-RC observation discipline

Between `1.0.0-rcN` and `1.0.0`, defects are triaged by category:

| Priority | Category |
| --- | --- |
| P0 | correctness — wrong findings, crashes, data loss |
| P1 | compatibility — wire contract, API, schema breaks |
| P2 | precision — false positives/negatives |
| P3 | docs/UX — wording, ergonomics, examples |

Allowed changes in this window: false-positive fixes, false-negative
fixes, crash fixes, compatibility fixes, performance-regression fixes,
docs fixes, release fixes. Everything else waits for 1.x.

### Telemetry

No automatic telemetry is collected. RC feedback comes only from
user-reported issues, benchmarks, the real OSS corpus, dogfooding, and
external adopters.

### Compatibility rule

No breaking change to `forge-contracts/1` during RC. If a break is
unavoidable: restart RC numbering (`rcN+1`) and document the migration.

## 5. Claim-to-evidence

No product capability claim ships without implementation, a proof
artifact, and a regression gate — see `CONTRIBUTING.md` and
`docs/architecture.md`. Release claims may only restate what the proof
artifacts (`golden/metrics.json`, `docs/benchmarks/`, `docs/releases/`)
already demonstrate.

## 6. Release engineering

- RC artifacts: wheel, sdist, SBOM, SHA256SUMS, `release-manifest.json`,
  `provenance.json`, contract schemas, env manifest — all produced by
  `tools/release_candidate.py`.
- Dirty trees are refused by default (`--allow-dirty` override).
- Version disagreement between `pyproject.toml`, wheel, sdist, and the
  manifest fails the dry run.
- Contract schema drift during RC fails `tools/rc_baseline.py --check`
  and requires explicit approval per §1.
- Publishing is manual-only (`workflow_dispatch`) and prefers PyPI
  Trusted Publishing; see `docs/release.md`.
